# Databases, artifacts and data isolation

## Decision

**PostgreSQL (Supabase) for hosted collaboration and durable work; SQLite for the local engine; private operator-owned files for all repair evidence.** Separate high-value identity/workspace/project/run metadata from high-volume trajectories, code, artifacts and datasets. Both repair paths — the one-shot CLI and the durable worker — keep their evidence in operator files, and only a bounded result crosses into the control plane. Do not add a second hosted database or duplicate identity authority without a concrete requirement. **D1 is explicitly not part of this path** — it is listed below only as a reference for why the choice was rejected, not as a component.

Three stores exist and they are not interchangeable:

| Store | Authority over | Not used for |
| --- | --- | --- |
| Supabase Auth + PostgreSQL (hosted, deployed) | Hosted identity, workspaces, projects, grants, private conversations, durable work items/runs/leases/events, repair policies and one bounded repair result per accepted attempt | The local engine's identity; any repair receipt, trace, prompt, candidate archive or expected value; large blobs |
| SQLite (local self-hosted engine) | A **separate** local identity, local projects, analyses, jobs and events on one host | Hosted identity, multi-host writes, shared network filesystems |
| Private filesystem (both repair paths: one-shot CLI and durable worker) | Operator-owned configuration, source/candidate archives, receipts, traces, patches and private expected values | No automatic publication or web serving; the durable worker reports a bounded result and bounded numeric progress and nothing else; sanitized public samples are separate reviewed build assets |

The hosted Supabase identity and the local FastAPI/SQLite identity are deliberately distinct and are not bridged: a hosted session is never forwarded into the local engine, and a cloud project is not an executed local project.

## Current local state

The local FastAPI engine uses SQLite for users, sessions, OAuth state, projects, analyses, jobs and events; its worker uses leases and bounded retries. SQLite WAL is not a multi-host shared-network-filesystem store. Hosted React collaboration instead uses the configured Supabase Auth/PostgreSQL project once its migrations are applied.

## Hosted control-plane DB (deployed)

Supabase Auth and PostgreSQL are the selected hosted collaboration boundary, and this is no longer only a target: the migrations are applied to the production project. Existing workspace/chat tables are extended by `projects`, `project_memberships`, `project_invitations` and `project_audit_events`. RLS filters reads; narrow RPCs own project writes and grant changes. Durable work, runs, worker leases and run events live in this same authority rather than in a second queue, broker or D1 database; approvals and evidence metadata belong there too. What is deployed is the **control plane**, not a runtime: rows describing work exist, but no hosted process executes it.

`supabase/migrations/durable_factory_runtime.sql` adds `work_items` (accepted work with its frozen source identity, input digest, attempt counters and cancellation record), `factory_runs` (one attempt each, with phase, checkpoint, resolved snapshot identity, bounded result and lease expiry), `factory_run_events` (append-only typed log, capped at 200 rows per run) and `project_workers` (per-project worker registrations). The fencing token is deliberately not among them: it lives in `private.factory_run_leases`, an unexposed schema on which `anon` and `authenticated` hold no privilege, so a user-facing read of a run cannot return a live lease. On the four public tables `authenticated` holds SELECT only, and all mutation is through the migration's SECURITY DEFINER RPCs. Every text column is an identifier, a short enumerated code or a bounded derived detail, and the two JSONB columns are structurally validated, so there is no free-text column into which a credential or host filesystem path could be written.

Apply `retained_attribution_and_lease_clock.sql` after that runtime migration. Accepted project invitations/chat shares and cancelled work retain their state and timestamps when an attribution account is deleted; the actor foreign key may become null, but grants still require a matching live actor. Lease deadlines, expiry checks and reclaim decisions use `clock_timestamp()` after relevant locks. Event/audit timestamps retain transaction-time semantics. Workspace deletion with run history remains a supported cascade, while deleting a referenced worker registration on its own remains forbidden.

Apply `controlled_repair_runtime.sql` last. It is additive and repeatable, and it keeps the second task kind inside the same authority rather than adding a queue, a broker or a second database. It adds `project_repair_policies` — the enrollment record binding one project, one worker Auth identity, one frozen public GitHub URL/owner/repo/commit and one reviewed configuration SHA-256 — plus `repair_policy_id` and a bounded `goal` column on `work_items`, kind-dependent constraints that require a repair row to carry its policy, goal and source pin from admission while an analysis row carries none of them, and a per-run trigger that makes the phase enum and the result shape per kind structural rather than merely enforced by the calling RPC. Policy identity, source and configuration are immutable at the table level; only revocation, cleared attribution, the clearing of the live worker reference and the worker's `last_seen_at` may change. `last_seen_at` is last authenticated contact, it only moves forward, and no scheduling decision reads it, so it is not capacity or availability. `authenticated` holds SELECT only on the new table and `anon` holds nothing, so enrollment and revocation exist only through the migration's two owner/admin RPCs.

The retained-record rule from `retained_attribution_and_lease_clock.sql` is applied twice here. A revoked policy is disabled, never deleted, because work history still names it, and `created_by`/`revoked_by` may become null when an account is deleted — authority is always re-derived from current project roles and worker designations rather than read from those columns. The worker identity itself is split for the same reason: `worker_identity` is the frozen, foreign-key-free, immutable record of what an operator approved and survives the account, while `worker_user_id` is the live reference that every authorization check and the RLS predicate read and that is *cleared* — never redirected, never restored — when the account is deleted, which withdraws the enrollment and settles its unfinished work in the same statement. A null live identity is a refusal everywhere. The consequence is that offboarding a worker account succeeds and leaves the approval record and the repair history intact, while deleting a policy that still has work history remains refused.

Repair work keeps the same no-free-text property as analysis work. The only client-supplied text that reaches the database is the bounded human goal, which submitting deliberately shares with the project. A repair checkpoint admits only a closed step enum, bounded non-negative counters, two hashes and one boolean, with any unknown key refused; a repair result admits exactly fifteen typed, bounded fields and its patch hash is recomputed in SQL before the row is accepted. An over-limit patch is refused rather than stored truncated. Commands, check output, the operator's expected acceptance values, model trajectories, container names and host paths therefore have no column to occupy.

## Per-worker state

Disposable workers keep temporary source and execution files locally; authoritative checkpoints, run state and evidence metadata must survive the runner. Keep repositories, datasets, model weights, screenshots and large logs in permission-scoped filesystem/object storage. A Rust rewrite is not part of the selected implementation path.

The durable analysis worker follows that split: each attempt's GitHub snapshot is extracted into a disposable per-run directory on the worker's own disk and deleted when the attempt ends, successfully or not. Nothing of a crashed attempt's working directory is recovered; what survives is the work item, the run row, its checkpoint and its recorded snapshot identity.

The controlled repair worker follows the same split, with one more boundary. Its disposable per-run tree — the fetched snapshot, the frozen configuration copy, the goal file and the child's result and stderr files — lives under its `--work-root` on the worker host and is removed when the attempt ends; a hard kill leaves it for the next startup sweep, which removes only marked directories whose owning process is gone. Its **durable private evidence** is separate and is deliberately retained: a fresh `0700` directory per attempt under the operator's `--evidence-root`, namespaced by work item and then by run, attempt and a random suffix, holding the resolved configuration, the source archive, the receipt, the ordered trace, baseline and verification results, the candidate archive, the diff and an operator-only index of the attempt. None of that is in either database and no endpoint serves it. What the control plane receives is the bounded result and bounded numeric progress; what survives a crash is the work item, its frozen source, pin, goal and policy binding, and the run row with its checkpoint.

The local repair/reverification CLI deliberately does **not** follow that split, because it has no control plane to report to. Its disposable workspace lives under an operator-owned `0700` run root and is removed on normal completion, cancellation or ordinary failure; a hard kill can leave it behind. Its durable output is a new private `0700` evidence directory per run, never an existing one. That directory retains the resolved configuration, the original source archive, any candidate archive, the checkpointed receipt, the ordered JSONL trace, baseline and verification results, and the patch. **It contains real source, prompts, model output and the operator's private expected values, so it must be treated as confidential and retained or deleted under the operator's own policy.** No raw evidence file is automatically published, indexed, served or referenced by either database, and no hash in it authenticates its producer. Publishing anything derived from a run is a separate, deliberate act: the public `repair-example.json`/`repair-example.patch` assets were extracted and sanitized by hand from one historical run, and that is the only path by which run-derived material has ever become public.

## When to choose PostgreSQL / Supabase

The dedicated Oryveta project is configured in the public client defaults. Base workspace/private-chat schemas, the project-membership migration, the durable-runtime migrations and the controlled repair migration are in `supabase/`; apply them in the documented prerequisite order. Exposed tables require explicit grants plus tested RLS, appropriate indexes and backup/restore procedures. Free-plan limits cannot support an unconditional uptime promise and are a fact to plan around rather than work around: a Free project is paused after about a week of inactivity, and the Free plan provides no automatic backups, so the durable queue that both task kinds depend on is neither continuously available nor automatically recoverable at this tier. Generating artificial traffic to prevent a pause is not an acceptable practice here.

## Auth/storage rules

Do not duplicate conflicting session systems unintentionally (Better Auth vs Supabase Auth). Never send service-role keys to browsers; no worker holds one either, including the repair worker, whose authority is an ordinary Auth session plus an enabled registration plus an enabled policy. Separate customer project data and model memory by tenant, with retention, consent and deletion rules. Repair evidence — from the one-shot CLI and from the durable worker alike — has no tenant model at all: its only boundary is operator file ownership and `0700` permissions on the host, so one operator's evidence must never be placed on shared storage with other tenants' work. Nothing in an evidence root expires on its own and the control plane will never tell an operator when to delete it, so retention and deletion must be a written, deliberate operator decision.

## Recovery

Encrypt backups; test restorations; keep schema migrations in Git; define recovery-point/recovery-time objectives for real customer use. Cryptographic hashes verify artifact integrity, not software correctness. This repository establishes **no** backup, restore-drill, recovery-objective or availability evidence — whatever a given deployment's provider or operator may do independently, none of it is documented, exercised or committed to here, so no such claim may be made on Oryveta's behalf.
